# 設計說明

記錄這個專案的架構、當初的取捨，以及之後要改東西時該注意什麼。

日期：2026-10-06

---

## 一、要解決什麼問題

規劃一趟多人旅行時，通常要同時處理三件事：

1. **行程**：哪天幾點去哪裡
2. **分帳**：誰付了什麼、最後誰要還誰多少
3. **打包**：東西有沒有帶齊

這三件事現在散在不同的 App、Google 試算表、聊天記錄裡。這個工具把它們放在同一個地方，而且不用註冊帳號。

---

## 二、關鍵決定

### 1. 資料存在瀏覽器（localStorage），不用伺服器

**為什麼：** 不用註冊、不用付錢、隱私最好、永遠不會因為某個雲端服務關掉而壞掉。

**代價：** 換裝置資料就不見，多人無法即時共同編輯。

**怎麼補：**
- 一定要有「匯出 / 匯入備份檔」，而且在首頁明顯提醒
- 提供唯讀分享連結，讓同行的人至少看得到

**當初比較過的方案：**

| 方案 | 結論 |
|------|------|
| Supabase | ❌ 免費方案閒置一週會自動暫停。旅遊工具可能幾個月才用一次，每次都要先去後台喚醒，不可接受 |
| Firebase | ⭕ 不會因閒置暫停、免費額度充足。但要申請專案、貼金鑰，而且沒有登入的話安全只能靠「連結難猜」 |
| 本機 + 唯讀分享 | ✅ 採用。零設定、零維護，而且多數情況旅伴只需要「看得到」而不是「一起改」 |

### 2. 資料結構以「一趟旅程 = 一個完整物件」為單位

即使現在存在本機，`trip` 物件是自我完整的（成員、匯率、行程、支出、清單全在裡面）。
日後真的要加雲端同步時，一個 trip 可以直接當成雲端的一筆資料，不需要重寫其他模組。

### 3. 分享連結把資料壓進網址的 `#` 片段

- 用瀏覽器內建的 `CompressionStream('gzip')`，不需要任何套件
- `#` 後面的內容依照網路標準不會送到伺服器，連 GitHub 都看不到內容
- 一趟 5 天、4 個行程點、41 項清單的旅程，連結約 2,100 字元，LINE 可以正常傳
- 連結超過 8,000 字元時會在畫面上提醒改用備份檔

### 4. 金額一律用「整數的分」計算

`0.1 + 0.2 !== 0.3` 是浮點數的經典問題，算錢不能出這種錯。
所有金額進入 `settle.js` 時都先 `Math.round(x * 100)` 轉成整數，最後才除回去顯示。

除不盡時（例如 100 元分 3 人），餘數一分一分發給前面的人，
確保 **分攤總和完全等於原金額**，不會少一塊錢。這一點有專門的測試守著。

### 5. 用上移／下移箭頭，不用拖曳

拖曳在手機上容易誤觸、也容易做壞。箭頭手機電腦都好按，而且第一項的「上移」和
最後一項的「下移」會自動變灰，不會出現無效操作。另外提供「依時間排序」一鍵整理。

### 6. 純前端，沒有框架、沒有建置流程

用傳統的 `<script>` 標籤載入，不用 ES modules（ES modules 在 `file://` 會被瀏覽器的
安全限制擋住）。這樣檔案丟進 GitHub 就是一個能用的網站，也不會因為某個套件更新而壞掉。

## 三、模組切分

每支檔案只管一件事，彼此透過明確的介面溝通：

| 檔案 | 負責 | 依賴 |
|------|------|------|
| `settle.js` | 分帳計算。**純函式，完全不碰畫面**，所以容易測試 | 無 |
| `store.js` | 讀寫 localStorage、旅程 CRUD、日期換算、備份匯出匯入 | 無 |
| `share.js` | 分享連結的編碼與解碼 | `store.js`（只用 `migrateTrip`） |
| `ui.js` | 共用元件：表單視窗、浮動提示、複製、下載、選檔 | 無 |
| `trips.js` / `itinerary.js` / `expenses.js` / `checklist.js` | 各自一個分頁的畫面與互動 | `store` `ui` `settle` |
| `app.js` | 分頁切換、分享、唯讀模式、啟動 | 全部 |

畫面採「資料變了就整頁重畫」的做法。對這個規模來說，比起精細控制局部更新，
整頁重畫簡單很多，也不會出現畫面和資料對不上的 bug。

## 四、容易出錯的地方（改程式前先看這裡）

1. **成員被刪掉，但舊支出還指著他**
   `settle.js` 會過濾掉不存在的成員，並發出警告，不會讓計算爆掉。改動時要維持這個行為。

2. **幣別代碼改名**
   改幣別代碼時，`trips.js` 會一併更新所有用到該幣別的支出，否則那些支出會查不到匯率。

3. **行程點與支出的雙向連結**
   行程點填了金額可以「加到分帳」，產生的支出帶有 `fromItemId`，行程點帶有 `expenseId`。
   - 改行程點的金額 → 同步更新支出
   - 改支出的金額 → 同步更新行程點
   - 刪除支出 → 要清掉行程點的 `expenseId`，否則會顯示「已加入分帳」但其實已經沒有了

4. **旅行天數變少**
   `store.syncDays()` 會砍掉多出來的天，並把「有內容」的那幾天回傳給呼叫端，
   由 `trips.js` 提示使用者。不要讓行程安靜消失。

5. **改完 js/ 或 css/ 要把版本號加 1**
   `index.html` 裡每個 js/css 連結後面有 `?v=N`。沒有把 N 加 1 的話，
   使用者的瀏覽器會沿用舊檔，造成新舊程式混在一起 —— 這個實際發生過，
   症狀是「新功能的按鈕沒出現」，很容易誤判成程式壞掉。

6. **localStorage 可能失敗**
   無痕視窗、空間滿了都會讓儲存失敗。`store.save()` 會攔下來提示使用者去下載備份。

## 五、測試

分帳是唯一「算錯會有實質損失」的部分，所以測試集中在這裡（15 項）：

- 基本均分、部分成員分攤、單人自付
- 淨額總和必為 0（錢不會憑空生出或消失）
- 除不盡時的餘數分配
- 外幣匯率換算
- 匯率沒設定、分攤名單為空、付款人或成員已被刪除等異常情況
- 結算轉帳總額正確、結算後每人歸零、轉帳筆數最少
- 浮點數誤差

`tests/settle.tests.js` 是唯一一份測試內容，`tests/test.html`（瀏覽器）和
`tests/run.js`（終端機）都載入它，不會出現兩套互相矛盾的測試。

## 六、之後可以加的東西

- 行程點之間的交通時間估算
- 多幣別的結算分別顯示（目前一律換算成基準幣別）
